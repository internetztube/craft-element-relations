# Element Relations (Craft CMS plugin)

Shows where an element is used. Relations are extracted on element save into `{{%elementrelations_cache}}` (via queue jobs) and read back through `RelationsModel` (Twig, GraphQL, CP field).

## Working on it
- `dev/dev.sh` creates/starts a Craft 5 dev project in `../craft-element-relations-dev` (PostgreSQL via Homebrew). `up|serve|stop|queue|seed|smoke|reset`.
- `dev/dev.sh smoke` seeds content and runs `dev/smoke.php`, the regression test. Run it after every change, ideally on both databases (`DB_DRIVER=mysql PROJECT_DIR=... dev/dev.sh smoke`). `dev/dev.sh e2e` starts the dev server and runs `dev/e2e.php`, which drives the control panel over HTTP (login, edit page, Craft's element-index endpoint, the replace endpoints) and catches what the console smoke cannot (request validation, permissions, the ids the index really sends). `dev/dev.sh ui` runs `dev/ui.mjs`, the same control panel in headless Chrome (`dev/browser.mjs`: CDP, no packages): what a person sees, lists, dropdown badges, columns, the wizard, replace and undo, the delete dialog, an editor without the permission. `dev/dev.sh ci` = smoke + e2e + ui; `dev/dev.sh coverage` = ci with line coverage of `src/` (pcov, `dev/coverage.php` prepended to every PHP process incl. the queue, and started by `dev/coverage-router.php` for the dev server's pages (PHP's built-in server prepends nothing to its router); `dev/coverage-report.php` merges and fails below `COVERAGE_MIN`, 98 %), what GitHub Actions runs (`.github/workflows/ci.yml`); keep the two in sync by changing the script, not the workflow. Every feature needs a test in one of the three suites; ci regenerates `dev/TESTS.md` (`dev/tests-md.php`), one sentence per assertion, so what is covered can be read without the code. Numbers count elements: an element used in two sites, or through two fields, is one row and counts once everywhere (list footer, badges, wizard, notices, history, delete dialog, Twig, CLI); the Site column names every site.
- The seed also builds a demo site (`dev/demo.php`, "Transit", for screenshots; photos from unsplash.com/@internetztube, downloaded on the first seed) in the same project; its handles must not collide with the test fixtures, and `dev/smoke/demo.php` checks it.
- Every extractor is also the replacer for its field/element type (`InterfaceFieldReplacer` / `InterfaceElementReplacer`, implemented on the extractor class). A new extractor without a replacer is incomplete; each integration smoke runs `replaceRoundTrip()` (dev/smoke.php) on the seeded content.
- `vendor/bin/phpstan` must stay clean (level 9, `phpstan.neon`). Every PHP file declares `strict_types=1`: cast DB rows, request params and decoded JSON at the boundary.
- Craft 5.3+ only (3.2+). No custom list UI and no build step: the field renders Craft's element index over the virtual `elements/Usage` type (abstract on purpose, see its docblock) filtered by the `usesElement` query param (`behaviors/ElementQueryBehavior`). The field's index carries its target as a base condition (`elements/conditions/UsesElementConditionRule`, hidden from "Add a filter" by its `usesElement` param), so every index request, the filter HUD's included, knows the list's element types. `UsageQuery` left-joins the entries/assets/categories/tags/users tables into Craft's inner and outer query and takes their stock params (`sectionId`, `filename`, `groupId`, …), so Craft's own sort options (`Usage::defineSortOptions()`) and filter rules (`elements/conditions/UsageCondition`) of the types in the list (`Usage::listedTypes()`) work unchanged. Inline JavaScript only: the type and site dropdowns (`templates/_field/filter-menu.twig`, injected via the `cp.elements.toolbar` hook) and, Pro, the replace flow.
- Extractors are registered in `ExtractorService::FIELD_EXTRACTORS` / `ELEMENT_EXTRACTORS` (built-ins; always iterate `ExtractorService::fieldExtractors()` / `elementExtractors()`, which add the ones registered via events). Element extractors declare `elementTypes()`. Pro permissions: `ElementRelations::canReplace()` / `canRollBack()`. Log with category `element-relations` (own log file).
- Scale: elements may have tens of thousands of usages. Lists and counts stay paginated/SQL; a replacement's and a rollback's reported counts are measured from the cache over the owners they changed (`ReplaceService::elementCount()`: the changed owners that no longer use / use again the element), never tallied per save, so a source deleted or edited by someone else meanwhile is not counted; replacements and rollbacks run as batched jobs over a fixed plan (`services/ReplaceRun` / `RollbackRun`, state in the operation record, changes as rows in `elementrelations_replacement_changes`, written right after each save). `dev/stress.php` is the load test (own project: `PROJECT_DIR=../craft-element-relations-stress PORT=8083 dev/dev.sh up`).
- Trashed elements keep their cache rows (lists, counts, the unused filter, the sort and replacements skip them via `dateDeleted`; restoring needs no refresh); nested elements (Matrix blocks Craft trashes when removed) and hard deletes drop theirs.
- Non-element usages (plugin settings) in `RelationsModel::GLOBAL_USAGE_PROVIDERS`; they are cache rows with `sourceElementId = null` and a `globalKey`, written by the provider's `refresh()` (settings-record events + full rebuild), not computed at read time.
- Editions: `ElementRelations::editions()` offers Pro only when the `features.editions` flag in `config/element-relations.php` is on (the dev seed writes that file); gate Pro behaviour with `ElementRelations::isPro()`, decided per call (never at init). Pro today: `unused()` query param + `elements/conditions/UsedConditionRule` (the “Used anywhere” filter; no extra index source on purpose: the filter works on top of every source and respects its permissions), `elements/actions/ReplaceUsages` (“Replace…” on the usages ticked in the field's list; `Usage::actions()` returns only it, so Craft shows checkboxes, and none of Craft's default actions) and `ReplaceRelations` (“Replace everywhere…” on element indexes), both opening the wizard (a `CpScreenSlideout`: `templates/_field/replace.twig` opens `ReplaceController::actionWizard()` / `_field/wizard.twig`; scopes: ticked, all in the filtered list, everywhere) on `services/ReplaceService` (`PRO_ELEMENT_TYPES`). The control panel always queues (`replace(queue: true)`, `queueRollback()`, `jobs/ReplaceElementJob` / `RollbackJob`) and the field polls `actionStatus()`; the CLI (`console/controllers/ReplaceController`) and migrations run synchronously. `services/InUseGuard` blocks deleting / taking offline elements with live usages in the control panel's element actions (`ElementRelations::guardsInUse()`, permission `PERMISSION_IN_USE`); on Craft 5.10+ `elements/deletionblockers/InUseDeletionBlocker` puts them in Craft's delete dialog. Detection/display stays free.
- `CHANGELOG.md` has an `Unreleased` section; add user-facing changes there.
