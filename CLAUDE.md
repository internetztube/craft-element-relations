# Element Relations (Craft CMS plugin)

Shows where an element is used. Relations are extracted on element save into `{{%elementrelations_cache}}` (via queue jobs) and read back through `RelationsModel` (Twig, GraphQL, CP field).

## Working on it
- `dev/dev.sh` creates/starts a Craft 5 dev project in `../craft-element-relations-dev` (PostgreSQL via Homebrew). `up|serve|stop|queue|seed|smoke|reset`.
- `dev/dev.sh smoke` seeds content and runs `dev/smoke.php`, the regression test. Run it after every change, ideally on both databases (`DB_DRIVER=mysql PROJECT_DIR=... dev/dev.sh smoke`). `dev/dev.sh e2e` starts the dev server and runs `dev/e2e.php`, which drives the control panel over HTTP (login, edit page, Craft's element-index endpoint, the replace endpoints) and catches what the console smoke cannot (request validation, permissions, the ids the index really sends). `dev/dev.sh ui` runs `dev/ui.mts`, the same control panel in headless Chrome (`dev/browser.mts`: CDP, no packages): what a person sees, lists, dropdown badges, columns, the wizard, replace and undo, the delete dialog, an editor without the permission. `dev/dev.sh ci` = smoke + e2e + ui; `dev/dev.sh coverage` = ci with line coverage of `src/` (pcov, `dev/coverage.php` prepended to every PHP process incl. the queue, and started by `dev/coverage-router.php` for the dev server's pages (PHP's built-in server prepends nothing to its router), opcache off (its optimizer hides lines from pcov); `dev/coverage-report.php` merges and fails below `COVERAGE_MIN`, 100 %: every line of `src/` runs in a test, delete a guard that cannot trigger instead of excluding it), what GitHub Actions runs (`.github/workflows/ci.yml`); keep the two in sync by changing the script, not the workflow. Every feature needs a test in one of the three suites; ci regenerates `dev/TESTS.md` (`dev/tests-md.php`), one sentence per assertion, so what is covered can be read without the code. Numbers count elements: an element used in two sites, or through two fields, is one row and counts once everywhere (list footer, badges, wizard, notices, history, delete dialog, Twig, CLI); the Site column names every site.
- The seed also builds a demo site (`dev/demo.php`, "Transit", for screenshots; photos from unsplash.com/@internetztube, downloaded on the first seed) in the same project; its handles must not collide with the test fixtures, and `dev/smoke/demo.php` checks it.
- Every extractor is also the replacer for its field/element type (`InterfaceFieldReplacer` / `InterfaceElementReplacer`, implemented on the extractor class). A new extractor without a replacer is incomplete; each integration smoke runs `replaceRoundTrip()` (dev/smoke.php) on the seeded content.
- The dev scripts (`dev/browser.mts`, `ui.mts`, `screenshots.mts`) are TypeScript that Node 24 runs as it is (type stripping: erasable syntax only, `.ts` imports; `.mts` because there is no `"type": "module"`); `dev/dev.sh typecheck` runs tsc (`dev/tsconfig.json`, strict) in CI's phpstan job. Values from the page (`evaluate()`) are `any`: declare the shape you read. The plugin's own JavaScript stays inline (no build step).
- `vendor/bin/phpstan` must stay clean (level 9, `phpstan.neon`). Every PHP file declares `strict_types=1`: cast DB rows, request params and decoded JSON at the boundary.
- Craft 5.3+ only (4.0+). No custom list UI and no build step: the field renders Craft's element index over the virtual `elements/Usage` type (abstract on purpose, see its docblock) filtered by the `usesElement` query param (`behaviors/ElementQueryBehavior`). The field's index carries its target as a base condition (`elements/conditions/UsesElementConditionRule`, hidden from "Add a filter" by its `usesElement` param), so every index request, the filter HUD's included, knows the list's element types. `UsageQuery` left-joins the entries/assets/categories/tags/users tables into Craft's inner and outer query and takes their stock params (`sectionId`, `filename`, `groupId`, …), so Craft's own sort options (`Usage::defineSortOptions()`) and filter rules (`elements/conditions/UsageCondition`) of the types in the list (`Usage::listedTypes()`) work unchanged. Inline JavaScript only: the type and site dropdowns (`templates/_field/filter-menu.twig`, injected via the `cp.elements.toolbar` hook) and, Pro, the replace flow.
- Extractors are registered in `ExtractorService::FIELD_EXTRACTORS` / `ELEMENT_EXTRACTORS` (built-ins; always iterate `ExtractorService::fieldExtractors()` / `elementExtractors()`, which add the ones registered via events). Element extractors declare `elementTypes()`. Pro permissions: `ElementRelations::canReplace()` / `canRollBack()`. Log with category `element-relations` (own log file).
- Scale: elements may have tens of thousands of usages. Lists and counts stay paginated/SQL; a replacement's and a rollback's reported counts are measured from the cache over the owners they changed (`ReplaceService::elementCount()`: the changed owners that no longer use / use again the element), never tallied per save, so a source deleted or edited by someone else meanwhile is not counted; replacements and rollbacks run as batched jobs over a fixed plan (`services/ReplaceRun` / `RollbackRun`, state in the operation record, changes as rows in `elementrelations_replacement_changes`, written right after each save). `dev/stress.php` is the load test (own project: `PROJECT_DIR=../craft-element-relations-stress PORT=8083 dev/dev.sh up`).
- Trashed elements keep their cache rows (lists, counts, the unused filter, the sort and replacements skip them via `dateDeleted`; restoring needs no refresh); nested elements (Matrix blocks Craft trashes when removed) and hard deletes drop theirs.
- Non-element usages (plugin settings) in `RelationsModel::GLOBAL_USAGE_PROVIDERS`; they are cache rows with `sourceElementId = null` and a `globalKey`, written by the provider's `refresh()` (settings-record events + full rebuild), not computed at read time.
- Editions: `ElementRelations::editions()` offers Pro only when the `features.editions` flag in `config/element-relations.php` is on (the dev seed writes that file); gate Pro behaviour with `ElementRelations::isPro()`, decided per call (never at init). Pro today: `unused()` query param + `elements/conditions/UsedConditionRule` (the “Used anywhere” filter; no extra index source on purpose: the filter works on top of every source and respects its permissions), `elements/actions/ReplaceUsages` (“Replace…” on the usages ticked in the field's list; `Usage::actions()` returns only it, so Craft shows checkboxes, and none of Craft's default actions) and `ReplaceRelations` (“Replace everywhere…” on element indexes), both opening the wizard (a `CpScreenSlideout`: `templates/_field/replace.twig` opens `ReplaceController::actionWizard()` / `_field/wizard.twig`; scopes: ticked, all in the filtered list, everywhere) on `services/ReplaceService` (`PRO_ELEMENT_TYPES`). The control panel always queues (`replace(queue: true)`, `queueRollback()`, `jobs/ReplaceElementJob` / `RollbackJob`) and the field polls `actionStatus()`; the CLI (`console/controllers/ReplaceController`) and migrations run synchronously. `services/InUseGuard` blocks deleting / taking offline elements with live usages in the control panel's element actions (`ElementRelations::guardsInUse()`, permission `PERMISSION_IN_USE`); on Craft 5.10+ `elements/deletionblockers/InUseDeletionBlocker` puts them in Craft's delete dialog. Detection/display stays free.
- `CHANGELOG.md` has an `Unreleased` section; add user-facing changes there.

## Quirks (found the hard way)
Craft
- The Permissions screen saves no user element: per-user permission changes only fire `UserPermissions::EVENT_AFTER_SAVE_USER_PERMISSIONS` (group changes `EVENT_AFTER_ASSIGN_USER_TO_GROUPS`). Anything cached per user must listen to both.
- Craft caches element index queries for an hour, tagged by the listed type; usage lists change when *other* elements are saved, so `usesElement` / `unused` queries bypass that cache.
- The index JS always sends a `siteId`; listing every site needs `UsageQuery::$allSites`. The status menu's "Drafts" only works with `canHaveDrafts` in the index's jsSettings. Edit pages strip the URL hash (no deep links to a field).
- Tag and category group ids overlap: filter `groupId` per element type, never across.
- A site added after a category group exists reaches that group in project config only (the seed creates the second site first).
- Scripts that bootstrap Craft without `run()` never fire `EVENT_AFTER_REQUEST`, so the plugin's deferred refresh doesn't run: `php craft element-relations/resave-relations && php craft queue/run`.
- In site requests `status: null` / `drafts: null` would read as "not given": `RelationsModel` uses an explicit `DEFAULT`.
- MySQL returns numbers as strings (cast); PostgreSQL returns rows that tie on the sort in any order (sort in PHP before comparing).
- PostgreSQL binds at most 65,535 parameters per query, and an editor may see 100,000 usages: write long id lists into the SQL with `ElementRelations::idIn()`.
- A batched queue job can vanish (worker died, reservation lost): operations without progress for 10 min are resumed.
- Craft Solo has no user management (Authors / Last Edited By hidden, user-photo test uses the admin).
- Test tricks: `new Entry()` has no field layout; `Craft::$app->edition` can be set in memory; `Craft::$app->set('cache', null)` runs without a data cache; `Event::on()` on a class that isn't installed is harmless (no `class_exists` guard needed).

Plugins
- Hyper memoizes `getLinkTypes()`; a `setLinkTypes()` after it is not saved. Read `fields.<uid>.settings.linkTypes` from project config instead.
- Formie's form query limits itself to the control panel user's forms and builds `id = false` for a user with none, invalid SQL on PostgreSQL (4.0): load elements of any type through `ElementRelations::find()`, which uses Formie's `withoutCpIndexScope()`; the plugin checks permissions itself. Formie's own Forms field fails the same way on edit pages, so the demo's editors may view forms.
- Formie keeps encrypted (locked) values in `getContentState()->lockedValuesByUid`; call `hasLockedContent()` first, it loads the state. Form data is shared across sites (refresh the sibling sites, don't report them as skipped).
- Rich text: `||` appears in plain text; match reference tags as a whole.
- JSDoc inline object types `{ … }` in Twig-rendered scripts clash with `{{ }}`: use named typedefs.

Tests and coverage
- PHP's built-in server runs no `auto_prepend_file` for its router (`dev/coverage-router.php`), and `php -r` subprocesses skip it too (they `require ini_get('auto_prepend_file')` themselves).
- The built-in server (cli-server SAPI) uses `opcache.enable`, not `enable_cli`; its optimizer drops jumps like `continue;`, which then never show as covered. Coverage runs with opcache off. In the raw `.cov` files a line *absent* in a process was not executable there (optimized away); *miss* means it was executable and did not run. `dev/coverage-gaps.php` lists the uncovered lines.
- `PROJECT_DIR` must be absolute.
- A web request in a test that changes project config (saving plugin settings) leaves the test's own process with a stale copy: its next project-config write throws `StaleResourceException`. Do such requests last. A console `switchEdition()` reaches the web server only after `saveModifiedConfigData()`.
- Plugin settings fields are namespaced: the settings page renders `name="settings[protectInUse]"`.
- Long-lived dev databases hide ordering bugs in the seed: reproduce CI failures with `dev/dev.sh reset`.
- Each push runs CI twice (push + pull_request). Read the result with `gh run list --json conclusion` or `gh run view <id> --log-failed`, never from a piped `gh run watch`.
- Chrome on CI runners is slow (30 s to start); coverage slows the server further and exposes races. Wait for what Craft renders late (the "x of n" element count) before reading it.
- The Claude in Chrome extension's synthetic clicks don't fire DOM events on CP edit pages; check JS handlers through `javascript_tool`.
